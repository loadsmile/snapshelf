# SnapShelf Technical Overview

This is the technical source of truth for SnapShelf. It reflects the deployed Supabase backend and the existing Expo React Native app structure.

## Stack

- Expo SDK 54
- React Native 0.81
- Expo Router
- TypeScript strict mode
- Supabase Auth, Postgres, Realtime, Storage, and Edge Functions
- Local media storage through Expo FileSystem
- Vitest for helper-level unit tests
- Maestro for optional mobile smoke tests

## Architecture

```text
UI screens and components
  -> feature API modules in features/*/api.ts
  -> Supabase client in services/supabase.ts
  -> Supabase Auth/Postgres/Realtime/Storage
```

The app should keep backend-specific code inside feature API modules and `services/supabase.ts`. UI surfaces should call app-level APIs such as `createSnap`, `subscribeToShelves`, and `signIn` rather than constructing database queries directly.

## Backend Migration Status

SnapShelf has completed its Firebase-to-Supabase cutover. Disposable Firebase data was not migrated.

The migration replaced:

- `firebase` dependency with `@supabase/supabase-js`
- `services/firebase.ts` with `services/supabase.ts`
- Firebase environment variables with Supabase public variables
- Firestore document collections with Postgres tables
- Firestore security rules with Supabase Row Level Security policies
- Firestore `onSnapshot` listeners with Supabase Realtime channels
- Firebase account deletion with a Supabase Edge Function that uses the service role key server-side only

Implemented backend areas:

1. Done - Foundation: Supabase dependencies and config are in place, `services/supabase.ts` owns the client, and environment checks use Supabase public values.
2. Done - Auth and Profiles: sign-up, sign-in, sign-out, signed-out password recovery, email-confirmation deep links, SecureStore-backed native sessions, auth subscription, profile sync against `public.profiles`, and auth setup copy use Supabase.
3. Done - Shelves: `features/shelves/api.ts` uses Postgres, and Shelf subscriptions use Supabase Realtime channels that refetch Shelves after changes.
4. Done - Snaps and Pagination: `features/snaps/api.ts` uses Postgres, media remains local-first, Firestore cursors were replaced with `SnapCursor = { createdAt: string; id: string }`, and Tray/Library API shapes were preserved.
5. Done - Stacks and Threads: Stack and Thread APIs use Postgres, and live subscriptions use Supabase Realtime channels that refetch after changes.
6. Done - Account Deletion: the app verifies the password, snapshots current-device Snap/Shelf/Stack local media paths, invokes the deployed `delete-account` Edge Function, then deletes current-device local media after the backend deletion succeeds. The Edge Function source lives at `supabase/functions/delete-account`, and `SERVICE_ROLE_KEY` is configured as a server-side Supabase secret.
7. Done - Cleanup and Validation: obsolete Firebase files/config and dependencies have been removed after reference validation. `npm run typecheck` and `npm test` pass; run device QA with a disposable account before enabling production self-serve account deletion.
8. Done - Transactional Workflows: single and multi-image Snap creation, media replacement, and bounded bulk triage use Postgres functions with current-device cleanup only after confirmed persistence.

## Environment

Use only public Supabase values in the Expo app:

```env
EXPO_PUBLIC_SUPABASE_URL=https://your-project-ref.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-or-anon-public-key
```

Never expose the Supabase `service_role` key in Expo public environment variables. It belongs only in Supabase Edge Function secrets.

## Supabase Setup

1. Create a Supabase project on the free plan.
2. Enable the Email auth provider.
3. Keep `snapshelf://**` in the hosted project's Auth redirect URLs. The versioned config applies this pattern to the linked project.
4. Keep email confirmation enabled and test confirmation delivery and deep links on production builds.
5. Apply the versioned migrations under `supabase/migrations/`.
6. Enable Realtime for `shelves`, `snaps`, `stacks`, and `threads`.
7. Create a private Storage bucket named `snap-media` for future cloud media support.
8. Deploy the `supabase/functions/delete-account` Edge Function before enabling self-serve account deletion in production.

## Database Schema

`supabase/migrations/` is the executable source of truth. Use UUID primary keys generated by Postgres. Every user-owned table includes `user_id uuid not null references auth.users(id) on delete cascade`, and composite foreign keys prevent cross-account entity references.

```sql
create extension if not exists pgcrypto;

create table public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  email text,
  display_name text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.shelves (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null,
  cover_snap_id uuid,
  board_x double precision,
  board_y double precision,
  board_variant text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.snaps (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  shelf_id uuid references public.shelves(id) on delete set null,
  title text,
  image_url text,
  source_url text,
  thought text,
  labels text[] not null default '{}',
  source text not null default 'unknown',
  is_favorite boolean not null default false,
  favorited_at timestamptz,
  is_archived boolean not null default false,
  archived_at timestamptz,
  captured_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.stacks (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null,
  board_x double precision,
  board_y double precision,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.threads (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  from_type text not null default 'shelf',
  from_id uuid,
  from_shelf_id uuid,
  from_stack_id uuid,
  to_shelf_id uuid not null references public.shelves(id) on delete cascade,
  created_at timestamptz not null default now()
);

create table public.snap_media_locations (
  user_id uuid not null,
  device_id uuid not null,
  snap_id uuid not null,
  local_path text not null,
  primary key (user_id, device_id, snap_id)
);

-- Shelf and Stack manual covers use equivalent device-scoped tables:
-- public.shelf_cover_locations and public.stack_cover_locations.
```

Recommended indexes:

```sql
create index shelves_user_created_idx on public.shelves(user_id, created_at);
create index snaps_user_created_idx on public.snaps(user_id, created_at desc, id desc);
create index snaps_user_shelf_created_idx on public.snaps(user_id, shelf_id, created_at desc, id desc);
create index snaps_user_archived_idx on public.snaps(user_id, is_archived);
create index stacks_user_created_idx on public.stacks(user_id, created_at);
create index threads_user_idx on public.threads(user_id);
create index threads_user_to_shelf_idx on public.threads(user_id, to_shelf_id);
create index threads_user_from_shelf_idx on public.threads(user_id, from_shelf_id);
create index threads_user_from_stack_idx on public.threads(user_id, from_stack_id);
```

## Row Level Security

Enable RLS on every public table and keep policies simple: authenticated users can only access rows where `user_id` or `id` equals their auth UID.

```sql
alter table public.profiles enable row level security;
alter table public.shelves enable row level security;
alter table public.snaps enable row level security;
alter table public.stacks enable row level security;
alter table public.threads enable row level security;
alter table public.snap_media_locations enable row level security;
alter table public.shelf_cover_locations enable row level security;
alter table public.stack_cover_locations enable row level security;

create policy "profiles own rows" on public.profiles
for all to authenticated
using ((select auth.uid()) = id)
with check ((select auth.uid()) = id);

create policy "shelves own rows" on public.shelves
for all to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "snaps own rows" on public.snaps
for all to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "stacks own rows" on public.stacks
for all to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "threads own rows" on public.threads
for all to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

-- The three device-scoped media-location tables use the same user_id policy.
```

## Profile Trigger

Create a profile automatically after sign-up.

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
begin
  insert into public.profiles (id, email, display_name)
  values (new.id, new.email, new.raw_user_meta_data ->> 'display_name')
  on conflict (id) do nothing;
  return new;
end;
$$;

create trigger on_auth_user_created
after insert on auth.users
for each row execute procedure public.handle_new_user();
```

## Realtime

Enable Postgres changes for these tables:

```sql
alter publication supabase_realtime add table public.shelves;
alter publication supabase_realtime add table public.snaps;
alter publication supabase_realtime add table public.stacks;
alter publication supabase_realtime add table public.threads;
```

Feature subscriptions should keep the current public API shape:

- `subscribeToShelves(userId, callback, onError)`
- `subscribeToAllSnaps(userId, callback, onError, pageSize?)`
- `subscribeToTraySnaps(userId, callback, onError, cursor?, pageSize?)`
- `subscribeToShelfSnaps(userId, shelfId, callback, onError, cursor?, pageSize?)`
- `subscribeToStacks(userId, callback, onError)`
- `subscribeToThreads(userId, callback, onError)`

A simple and reliable implementation is to subscribe to table changes filtered by `user_id`, then refetch the relevant query after each change.

## Pagination

Firestore snapshot cursors should be replaced with a serializable cursor:

```ts
type SnapCursor = {
  createdAt: string;
  id: string;
};
```

Order Snap pages by `created_at desc, id desc`. For pages after the first cursor, query rows where `created_at < cursor.createdAt` or `created_at = cursor.createdAt and id < cursor.id`.

## Local Media Model

SnapShelf remains local-first for media.

- Snap images are stored under Expo `documentDirectory/snaps/`.
- Stack and Shelf cover images are stored locally.
- Supabase stores shared metadata such as title, thought, labels, source URL, Shelf assignment, Board position, and favorite/archive state.
- Local paths live in device-scoped location tables keyed by a SecureStore-backed installation ID.
- Snap creation and current-device media replacement run through transactional Postgres functions so metadata and path records cannot partially commit.
- Multi-image import supports up to 20 images, copies files sequentially, and creates all Snap/media rows in one transaction.
- Bulk Snap actions process at most 50 IDs per transaction and retain failed or uncertain items in UI selection.
- Missing local images are expected after reinstall, app data clear, OS cleanup, or signing into another device.
- Future media sync should use the private `snap-media` Supabase Storage bucket, but cloud image upload is not part of the current documentation-only prep.

## Storage Preparation

Create a private bucket for future Snap media:

```sql
insert into storage.buckets (id, name, public)
values ('snap-media', 'snap-media', false)
on conflict (id) do nothing;

create policy "snap media select own folder" on storage.objects
for select to authenticated
using (bucket_id = 'snap-media' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "snap media insert own folder" on storage.objects
for insert to authenticated
with check (bucket_id = 'snap-media' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "snap media update own folder" on storage.objects
for update to authenticated
using (bucket_id = 'snap-media' and (storage.foldername(name))[1] = (select auth.uid())::text)
with check (bucket_id = 'snap-media' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "snap media delete own folder" on storage.objects
for delete to authenticated
using (bucket_id = 'snap-media' and (storage.foldername(name))[1] = (select auth.uid())::text);
```

## Auth And Account Deletion

Supabase client auth supports sign-up, sign-in, sign-out, password reset, session persistence, and profile metadata updates.

Deleting an Auth user requires the service role key and must happen server-side. The app currently verifies the password and invokes an Edge Function named `delete-account`; the production-complete flow should be:

1. Client asks the user for their password.
2. Client verifies credentials by signing in or reauthenticating.
3. Client snapshots current-device local Snap, Shelf cover, and Stack cover media paths.
4. Client invokes the Edge Function with the user's session JWT.
5. Edge Function verifies the JWT, deletes any Storage objects owned by the user, then calls `supabase.auth.admin.deleteUser(user.id)`.
6. Client deletes the snapshotted current-device local media and signs out.

The service role key must be configured as a function secret, not in the app.

Deploy the function and secret with the Supabase CLI:

```bash
supabase secrets set SERVICE_ROLE_KEY=your-service-role-key
supabase functions deploy delete-account
```

## Main App Surfaces

- `app/_layout.tsx`: root providers, auth routing, share-intent routing, status/theme setup.
- `app/(auth)`: sign-in and sign-up screens.
- `app/(tabs)/board.tsx`: Board canvas, Shelves, Stacks, search, drag/zoom, and threads.
- `app/(tabs)/library.tsx`: full-account Snap retrieval, filtering, sorting, chips, and Snap detail entry.
- `app/(tabs)/tray.tsx`: active unsorted Snap triage queue.
- `app/(tabs)/settings.tsx`: account actions, theme, dev-only sample data, and local media checks.
- `app/shelf/[id].tsx`: Shelf detail and curation.
- `app/share-intent.tsx`: native share payload processing and Quick Snap save flow.
- `app/snap/[id].tsx`: exact Snap route used by post-save, Board search, and archive rediscovery entry points.

- `features/auth`: Supabase Auth, profile sync, auth context, account actions.
- `features/snaps`: Snap database APIs, atomic batch/bulk mutations, selection, pagination, search, archive rediscovery, Library filtering, presentation helpers, tests.


Maestro smoke flows live under `.maestro/` and can be run manually when a simulator or device is available:

```bash
maestro test .maestro
```

Use disposable Supabase test accounts for Maestro. Keep credentials out of committed YAML by passing `SNAPSHELF_TEST_EMAIL` and `SNAPSHELF_TEST_PASSWORD` as environment variables.

Do not claim confidence for native share intent, photo picker, file permissions, local file deletion, or account deletion from unit tests alone. Those flows need simulator or device QA.

## Backend Implementation Notes

- Implemented feature APIs now use Supabase for auth/profile, Shelves, Snaps, Stacks, and Threads.
- Realtime subscriptions intentionally refetch by `user_id` after table changes for correctness and to preserve existing UI API shapes.
- Snap Realtime refreshes coalesce changes that arrive while a refetch is in flight.
- Local media remains device-owned; Supabase stores local paths and metadata only.
- Obsolete Firebase files/config and dependencies were removed after the Supabase feature APIs replaced Firebase references.

## Technical Debt

- Account-deletion production readiness still needs device QA with a disposable account.
- Input validation is minimal before backend writes.
- No offline-first sync layer is implemented.
- Library and Board search are in-memory over subscribed or loaded Snap data.
- Realtime should initially refetch after table changes for correctness; optimize only if measured usage requires it.
- Device QA is still required for iOS and Android share intent and local media behavior.
